# Literature survey: Exact SHA-256 reproduction of regenerated CSV files in a locked environment

The question asks for a stringent form of computational reproducibility: whether independently executing a packaged workflow in a locked environment regenerates three CSV files whose bytes yield exactly the three stated SHA-256 digests. Prior work distinguishes this standard from merely obtaining scientifically equivalent results. Lamb and Zacchiroli define a reproducible build as one in which a designated source version and its dependencies always produce bit-for-bit identical artifacts [2]. Although their focus is compiled software, the same criterion applies directly to generated datasets: digest equality tests artifact identity rather than approximate numerical agreement. Abarenkov et al. similarly emphasize that scientific workflows require automation, unambiguous software versions, and accessible inputs, while warning that bit-to-bit reproducibility may depend on the underlying computing platform even when software is packaged [1]. Thus, a “locked environment” is necessary evidence of control, but it does not by itself establish that the outputs are deterministic.

The literature identifies several prerequisites for a credible independent test. Scientific workflow systems automate derivations and support provenance tracking and bookkeeping [4], which are important because a digest mismatch alone does not identify the responsible stage. PyRDM argues that recomputability requires access to source code together with all associated input and output data, and proposes automating their publication in citable repositories [3]. For the package in question, this implies that the experiment should preserve the exact package version, inputs, execution command, dependency versions, configuration, and resulting CSV files. The test should be conducted from a clean initial state without reusing cached outputs. Recording intermediate artifacts or workflow-stage metadata would make any failure diagnosable rather than merely observable. These controls also align with broader scientific software-engineering concerns about maintenance, reuse, and quality attributes [5].

SHA-256 provides a precise metric for the final comparison because it maps an input bit string to a fixed-length digest [6]. Its role here is not to establish scientific validity or semantic equivalence, but to provide a compact test of exact byte identity. SHA-256 is designed to be collision resistant, and current collision research remains focused on simplified, step-reduced variants rather than practical collisions in the full function [7]. Consequently, equality between a regenerated file’s digest and its stated digest is strong operational evidence that the compared byte streams are identical. The experiment should compute each digest directly from the generated file bytes and compare it to the corresponding expected value. All three comparisons should be reported separately, with the filename-to-digest mapping fixed in advance. If any comparison fails, byte-level or text-level diagnostics should examine likely nondeterminism in row ordering, floating-point formatting, line endings, character encoding, delimiters, quoting, timestamps, locale-sensitive output, and unstable iteration order. These are plausible mechanisms to test, but the retrieved sources do not establish which, if any, affect this particular package.

## Gap

The supplied literature establishes the rationale and standard for bit-for-bit reproducibility, but it does not report an independent execution of the package, identify the three expected digests, or verify the regenerated CSV artifacts. The specific open question is therefore empirical: after initializing the stated locked environment and executing the package from a clean state using the documented inputs and commands, does each regenerated CSV produce its assigned SHA-256 digest exactly? A useful experiment must return three explicit pass/fail comparisons and preserve sufficient environment and workflow provenance to distinguish genuine deterministic reproduction from accidental reuse of preexisting outputs. If a digest differs, the experiment should retain both expected and observed hashes and characterize the first byte-level differences rather than treating all mismatches as equivalent.
