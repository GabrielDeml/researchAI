# Experiment design: Topic **Can the publication root be made operationally trustworthy?** Publish the literal inventory root through a signed release, transparency log, or equivalent authenticated channel, and specify exactly how a verifier obtains and validates it. _(auto-enqueued follow-up from topic-can-all-raw-records-be-made-auditable-publ)_

**Hypothesis:** For 64 simulated split-view attacks in which a transparency service signs two checkpoints of the same tree size with different roots and supplies a valid inclusion proof within each fork, isolated inclusion-only verifiers will accept both views, whereas verifiers that exchange their latest checkpoints once and require equal-size checkpoints to have identical roots will detect all 64 forks; neither method will flag any of 64 consistent-log controls.

## Summary
Simulate 64 signed same-size split-view transparency-log forks and 64 consistent controls, then compare isolated inclusion verification with one-round signed-checkpoint gossip.

## Protocol
1. Use Python 3.11 or later with only the standard library plus `cryptography` and `matplotlib`; install with `pip install cryptography matplotlib`. Set Matplotlib's backend to `Agg`. Do not use network access, external datasets, clocks, or nondeterministic randomness.
2. Define `MASTER_SEED = SHA256(b"publication-root-gossip-experiment-v1").digest()`. Derive the transparency service's deterministic Ed25519 private-key seed as `HMAC-SHA256(MASTER_SEED, b"ed25519-private-key")`; construct an Ed25519 private key from those 32 bytes and derive its public key. Treat the resulting public key as verifier configuration pinned out-of-band: artifacts may contain signatures but must not supply or replace the verifier's trusted public key.
3. Implement the binary Merkle tree with exactly 64 leaves. Hash a record byte string as `SHA256(b"\x00" + record)`. Hash an internal node as `SHA256(b"\x01" + left_hash + right_hash)`. At every level, combine adjacent nodes `(0,1), (2,3), ...`; because 64 is a power of two, no odd-node rule is needed. The final 32-byte value is the literal inventory root.
4. Implement inclusion proofs as the six sibling hashes from leaf level to root, each paired with a side marker. For a left sibling compute `SHA256(b"\x01" + sibling + current)`; for a right sibling compute `SHA256(b"\x01" + current + sibling)`. A proof is valid only if its leaf index is in `[0,63]`, it has exactly six siblings with the sides implied by the index at each level, and its reconstructed root equals the checkpoint root.
5. Serialize a checkpoint for signing as the exact byte sequence `b"INVCHKPT-v1\n" + tree_size.to_bytes(8, "big") + root`, where `tree_size` is 64 and `root` is exactly 32 raw bytes. Sign these bytes with Ed25519. A release artifact contains the integer tree size, lowercase hexadecimal root, lowercase hexadecimal signature, target leaf index, the target record encoded as UTF-8 text, and the six proof siblings and side markers. The verifier obtains the literal root by reading the artifact's root field, decoding exactly 32 bytes, rebuilding the checkpoint serialization, and verifying the signature with the pinned public key before using the root.
6. Generate records using canonical compact JSON encoded as UTF-8 with sorted keys and separators `(',', ':')`. For experiment class `kind`, scenario `s`, and index `i`, create fields `{"index": i, "kind": kind, "nonce": HMAC-SHA256(MASTER_SEED, f"record|{kind}|{s}|{i}".encode()).hexdigest(), "scenario": s}`. Use `kind="attack"` for attack scenarios and `kind="control"` for controls. Assert that every scenario has exactly 64 distinct record byte strings.
7. Generate 64 attack scenarios numbered 0 through 63. For scenario `s`, build fork A from its 64 ordinary attack records. Set target index `t = (13*s + 5) % 64`. Set mutation index `m = (17*s + 3) % 64`; if `m == t`, replace `m` with `(m + 1) % 64`. Build fork B by replacing only record `m` with canonical JSON containing `{"index": m, "kind": "attack", "mutation": "fork-B", "nonce": HMAC-SHA256(MASTER_SEED, f"mutation|attack|{s}|{m}".encode()).hexdigest(), "scenario": s}`. Thus the target record at `t` is identical in both forks. Compute both roots and assert they differ. Sign both size-64 checkpoints. Give verifier A the signed fork-A checkpoint and a valid proof for target `t` in fork A; give verifier B the signed fork-B checkpoint and a valid proof for the same target record in fork B.
8. Generate 64 consistent-log control scenarios numbered 0 through 63. For each scenario, build one size-64 tree from its control records, set `t = (13*s + 5) % 64`, compute and sign its checkpoint, and give both verifiers identical copies of that checkpoint plus a valid inclusion proof for record `t`. Assert that the two checkpoint roots and sizes are equal.
9. Implement the isolated inclusion-only baseline. Independently for each verifier and artifact: decode and length-check the root and signature, verify the Ed25519 signature over the exact checkpoint serialization, hash the supplied record, validate the inclusion proof against the signed root, and accept only if all checks pass. It has no access to the other verifier's checkpoint. Record a local alert whenever an artifact is rejected. For each scenario, record dual acceptance when both isolated verifiers accept.
10. Implement the checkpoint-gossip comparison. First perform the same local signature and inclusion checks as the baseline. Then exchange the two verifiers' latest checkpoint tuples `(tree_size, root, signature)` exactly once. Independently validate both signatures using the pinned public key. If both signed checkpoints have equal tree size but different roots, emit a fork alert; if their sizes and roots are equal, emit no fork alert. All generated pairs have equal size, so no consistency-proof behavior for unequal sizes is part of this experiment.
11. Add implementation sanity checks outside the 128 scored scenarios: altering one bit of a signed root while retaining its signature must fail signature verification, and altering one proof sibling while retaining the signed checkpoint must fail inclusion verification. Abort rather than report results if either tampered artifact is accepted or if any generator assertion fails.
12. Write one CSV row per scored scenario containing class, scenario number, both roots, both local acceptance results, dual-acceptance indicator, and gossip-alert indicator. Also write a JSON summary containing all metric counts and rates.
13. Save `checkpoint_gossip_results.png` at at least 1200 by 700 pixels. Plot grouped bars for attack and control scenarios, with one bar per method showing the fraction of scenarios that emitted an alert: inclusion-only local rejection/alert and checkpoint-gossip fork alert. Fix the y-axis to `[0,1.05]`, label each bar with its numerator and denominator, and title the figure `Split-view detection from signed-checkpoint gossip`.
14. Treat inclusion-only as the baseline and one-round gossip as the comparison. Mark the hypothesis supported only if all of these exact thresholds hold: attack dual acceptance is 64/64 for inclusion-only verification; gossip detects 64/64 attacks; inclusion-only local alerts are 0/128 attack views and 0/128 control views; control dual acceptance is 64/64; and gossip alerts are 0/64 controls. Any failure of an exact threshold refutes the stated hypothesis.

## Metrics
- Attack dual-acceptance count and rate: number of the 64 attack scenarios in which both isolated inclusion-only verifiers accept their locally valid fork, divided by 64.
- Attack-view local alert count and rate: number of rejected attack artifacts among 128 individual fork views, divided by 128.
- Gossip fork-detection count and true-positive rate: number of the 64 attack checkpoint pairs that produce an equal-size/different-root alert, divided by 64.
- Control dual-acceptance count and rate: number of the 64 consistent controls in which both isolated verifiers accept, divided by 64.
- Control local false-alert count and rate: number of rejected control artifacts among 128 individual control views, divided by 128.
- Gossip control false-positive count and rate: number of the 64 consistent checkpoint pairs that produce a fork alert, divided by 64.
- Detection-rate improvement: gossip attack true-positive rate minus the inclusion-only attack fork-alert rate; the expected improvement is 1.0.

## Expected outcomes
- **If supported:** All 128 attack views pass signature and inclusion verification, yielding attack dual acceptance of 64/64; isolated inclusion-only verification detects 0/64 forks; one-round checkpoint gossip detects 64/64 forks because every attack pair has size 64 and unequal signed roots; all 128 control views are accepted; and both methods produce 0/64 control alerts. The figure therefore shows attack alert rates of 0.0 for inclusion-only and 1.0 for gossip, with both control alert rates at 0.0.
- **If refuted:** The hypothesis is refuted if even one attack scenario is not accepted by both isolated verifiers, if gossip misses even one of the 64 equal-size/different-root forks, or if either method flags any consistent control. Concretely, any attack dual-acceptance count below 64, gossip attack-detection count below 64, attack or control local-alert count above 0, control dual-acceptance count below 64, or gossip control false-positive count above 0 is a refuting result.
