# Experiment design: Topic Can the complete repository and release payload be published with a cryptographic archive digest, commit identifier, full file inventory, and SHA-256 table covering source, schema, lock file, Makefile, README, outputs, raw results, logs, mutation specifications, and figure? _(auto-enqueued follow-up from topic-can-a-complete-artifact-package-be-release)_

**Hypothesis:** On 20 valid synthetic releases containing every committed file plus explicitly declared generated outputs and exclusions, and 40 invalid releases containing either an omitted committed file, an undeclared extra file, or a tracked file falsely reclassified as generated, a role-aware repository-to-release reconciliation algorithm will classify all 60 correctly; strict commit/release set equality will reject all 20 valid releases, and a simple rule requiring only that committed paths be a subset of release paths will accept all 20 invalid variants containing undeclared extras.

## Summary
Generate 20 deterministic synthetic repository snapshots and 60 release packages, then compare strict path equality, committed-path subset checking, and cryptographically verified role-aware reconciliation on valid, omitted-file, undeclared-extra, and falsely-reclassified releases.

## Protocol
1. Implement the experiment in Python 3.11 or later using only the standard library plus matplotlib. Set the global seed to 20250308 and complete all work in a fresh directory named `artifact_reconciliation_experiment`.
2. Define 20 synthetic repositories indexed 0 through 19. Each repository must contain these six committed paths: `src/main.py` (source), `schema/schema.json` (schema), `requirements.lock` (lock file), `Makefile` (Makefile), `README.md` (README), and `mutations/spec.yaml` (mutation specification). It must also contain two uncommitted workspace paths, `.DS_Store` and `build/tmp.bin`, which are explicitly declared as exclusions. Generate deterministic, repository-index-specific UTF-8 content for every committed and excluded workspace file using the fixed seed and repository index.
3. For each repository, define four declared generated outputs: `outputs/summary.json` (output), `results/raw.csv` (raw results), `logs/run.log` (log), and `figures/result.png` (figure). Generate their bytes deterministically from the repository index and committed-file hashes. Create `figures/result.png` with a deterministic standard-library PNG writer using fixed dimensions, pixels, compression settings, and no timestamps or variable metadata.
4. Compute SHA-256 for every committed file. Compute the synthetic commit identifier as `sha256:` followed by the SHA-256 hex digest of canonical compact JSON containing the sorted list of committed entries, where every entry has exactly `path`, `size`, and `sha256`, keys are sorted, separators are `(',', ':')`, and UTF-8 encoding is used. The excluded workspace files and generated outputs must not contribute to this commit identifier.
5. For every release variant, create a deterministic uncompressed POSIX tar archive containing only payload files. Add members in lexicographic path order and set every tar member's mtime, uid, gid, uname, and gname to zero or the empty string and its mode to 0644. Compute the archive SHA-256 over the final tar bytes.
6. Store a sidecar `release_manifest.json` outside the tar archive. It must contain: format version; repository index; commit identifier; archive filename; archive SHA-256; sorted committed-file table; sorted declared-generated table; exact exclusion list `[".DS_Store","build/tmp.bin"]`; and a complete sorted payload inventory with `path`, `size`, `sha256`, and declared role for every tar member. Serialize it using the same canonical JSON rules as in step 4. The manifest itself is publication metadata and is not a payload member, preventing recursive archive hashing.
7. Construct one valid release for each repository, for 20 valid releases total. Its tar payload must be exactly the six committed files plus the four declared generated outputs. Neither excluded workspace file may appear. All hashes, inventory records, the commit identifier, and the archive digest must be correct.
8. Construct one undeclared-extra invalid release for every repository, for 20 such releases. Start from the corresponding valid payload and add `extras/undeclared_<index>.txt` with deterministic bytes, but do not add that path to the declared-generated table or committed table. Include it honestly in the full payload inventory and recompute the tar digest and manifest. Thus all six committed paths remain present and the only semantic defect is an undeclared payload path.
9. Construct one omitted-committed-file invalid release for repositories 0 through 9, for 10 such releases. Start from the valid release and remove one committed path selected as the committed-path list at position `index mod 6`. Leave the repository committed table and commit identifier unchanged, but make the payload inventory and archive digest accurately describe the reduced archive. The only semantic defect must be the missing required committed path.
10. Construct one falsely-reclassified invalid release for repositories 10 through 19, for 10 such releases. Keep the valid archive bytes and all paths, but select the committed path at position `index mod 6`, add that tracked path to the declared-generated table, and label its payload inventory role as generated rather than committed. Preserve its correct bytes and hash and recompute the sidecar manifest. The repository committed table and commit identifier must remain unchanged. The semantic defect is that a path known to be tracked is falsely declared generated.
11. The final labeled dataset must therefore contain exactly 60 cases: 20 valid, 20 undeclared-extra invalid, 10 omitted-committed-file invalid, and 10 falsely-reclassified invalid. Before evaluating algorithms, assert these counts and assert that every manifest inventory exactly matches the actual tar member paths, sizes, and SHA-256 values and that every archive digest verifies. Abort on any failed construction assertion.
12. Implement the strict-equality baseline. Let `C` be the set of committed paths from the repository snapshot and `P` the set of actual tar member paths. Accept if and only if `C == P`. Do not consult generated or exclusion declarations.
13. Implement the committed-subset baseline. Using the same sets, accept if and only if `C` is a subset of `P`. Do not reject undeclared paths and do not consult generated roles or exclusions.
14. Implement role-aware reconciliation without using the ground-truth case label. Recompute the commit identifier from the repository committed table; recompute the archive digest; read every tar member directly; and recompute the full path, size, and SHA-256 inventory. Accept if and only if all of the following hold: the manifest commit identifier equals the recomputed commit identifier; the manifest archive digest equals the recomputed archive digest; the manifest inventory exactly equals the actual archive inventory; every committed payload file has the repository-recorded hash; every declared-generated file has its declared hash; the declared-generated path set `G` is disjoint from `C`; every exclusion path belongs to the known uncommitted workspace set, no exclusion path belongs to `C` or `G`, and no exclusion path appears in `P`; and `P == C union G`. Any failed condition means reject.
15. Run all three algorithms on all 60 cases. Record one CSV row per case and algorithm with repository index, case type, ground-truth validity, predicted acceptance, correctness, and the failed role-aware checks if applicable. Save this as `outputs/per_case_results.csv`, and save aggregate counts and rates as `outputs/metrics.json`.
16. Compute acceptance rates separately for valid, omitted, undeclared-extra, and reclassified cases for each algorithm. Also compute role-aware overall accuracy, valid-release acceptance rate, invalid-release rejection rate, and rejection counts by invalid subtype; strict-equality valid-release rejection count; and subset-baseline acceptance count for undeclared-extra releases.
17. Create `outputs/reconciliation_acceptance.png` as a grouped bar chart with case type on the x-axis, acceptance rate from 0 to 1 on the y-axis, and separate bars for strict equality, committed subset, and role-aware reconciliation. Annotate every bar with its numerator and denominator, use a fixed figure size and color palette, and save at 150 DPI.
18. Mark the hypothesis `supported` if and only if role-aware reconciliation accepts exactly 20 of 20 valid releases and rejects exactly 40 of 40 invalid releases, strict equality rejects exactly 20 of 20 valid releases, and committed-subset checking accepts exactly 20 of 20 undeclared-extra releases. Otherwise mark it `refuted`. Write this decision and all component Boolean checks to `outputs/decision.json`.

## Metrics
- Role-aware overall accuracy: number of all 60 releases whose accept/reject result matches the label divided by 60; required value is 1.0.
- Role-aware valid acceptance rate: accepted valid releases divided by 20; required value is 20/20 = 1.0.
- Role-aware invalid rejection rate: rejected invalid releases divided by 40; required value is 40/40 = 1.0.
- Role-aware subtype rejection: rejected omitted releases out of 10, undeclared-extra releases out of 20, and falsely-reclassified releases out of 10; required values are 10/10, 20/20, and 10/10.
- Strict-equality valid rejection count: valid releases for which committed path set is not exactly equal to payload path set; required value is 20/20 rejected.
- Committed-subset undeclared-extra acceptance count: undeclared-extra releases satisfying committed paths subset of payload paths; required value is 20/20 accepted.
- Per-algorithm, per-case-type acceptance rate: accepted cases divided by the number of cases in each of the four case types, plotted in the PNG figure.
- Cryptographic construction integrity: number of releases with matching archive digest, exact full inventory, and correct listed file hashes; required value is 60/60 so semantic classification is not confounded by corrupted metadata.

## Time budget
10 minutes (ceiling 30).

## Expected outcomes
- **If supported:** Role-aware reconciliation achieves 60/60 correct classifications, accepting 20/20 valid releases and rejecting all 10 omissions, all 20 undeclared extras, and all 10 false reclassifications; strict equality accepts 0/20 valid releases; committed-subset checking accepts 20/20 undeclared-extra releases; and all 60 archives independently pass digest and inventory verification.
- **If refuted:** The hypothesis is refuted if role-aware reconciliation makes even one error, if strict equality accepts even one valid release, or if committed-subset checking rejects even one of the 20 undeclared-extra releases; any archive integrity failure also invalidates the run and requires fixing the generator before interpreting the hypothesis.
