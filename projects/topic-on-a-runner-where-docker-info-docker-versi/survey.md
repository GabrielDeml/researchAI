# Literature survey: On a runner where `docker info`, `docker version`, and `docker ps` pass, do all six primary and six replay executions complete within the 1,200-second timed section?

Containerization is widely presented as a way to preserve the software environment required for computational reproducibility. Nagler et al. argue that Docker containers can package scientific software together with exact dependencies, configuration, input files, scripts, and post-processing tools, reducing installation problems and enabling the same environment to run across Linux servers and cloud infrastructure [1]. Their account supports using successful Docker diagnostic commands as prerequisite checks: such checks establish that the client can communicate with a running Docker service and perform basic container-management operations. However, the source does not show that passing these checks guarantees successful or timely execution of a particular containerized workflow. Environment availability and workflow completion are distinct properties.

The broader reproducibility literature likewise treats rerunning an artifact as an empirical test rather than a consequence of successful environment setup. Arabas et al. identify practical reproducibility challenges in computational science, including differences among researchers and complications introduced by parallel and distributed execution [3]. CORE-Bench operationalizes computational reproducibility through tasks that require agents to reproduce study results from supplied code and data, reinforcing the importance of end-to-end execution rather than setup alone [5]. These perspectives suggest that the relevant unit of observation here is each complete run. A runner should therefore be classified separately on at least three dimensions: whether Docker readiness checks pass, whether each primary or replay execution terminates successfully, and whether it terminates before the 1,200-second boundary.

The requirement for six primary and six replay executions addresses run-to-run variability, which is especially important when completion is governed by a hard timeout. Berndt et al. show that tests can pass or fail without code changes and that timeouts can be a major source of such flakiness [2]. In their SAP HANA setting, timeout failures accounted for 70% of flaky test failures, while repeated executions of the same code revision were used to estimate flakiness [2]. Although that industrial system differs substantially from a twelve-run Docker experiment, its methodology is directly relevant: repeated runs should be recorded individually, and timeout expiration should not automatically be interpreted as a deterministic artifact defect. It may instead reflect runtime variance, resource contention, or an inadequately calibrated threshold. Reporting only a mean or median duration would also be insufficient because the stated criterion is conjunctive—all twelve executions must finish within the timed section. Appropriate metrics are therefore the number and proportion completed within 1,200 seconds, the maximum elapsed time, separate primary and replay completion counts, and the identity and failure mode of every non-completing run.

Workflow research further cautions that container availability does not eliminate execution-level anomalies. KubeAdaptor reports that interactions between workflow scheduling and container orchestration can degrade execution efficiency [7], while Flow-Bench characterizes complex workflows as vulnerable to failures and performance degradation in heterogeneous environments [10]. Neither study evaluates this exact single-runner Docker setup, but both support collecting execution traces that distinguish container startup, task failure, abnormal termination, and timeout. For this experiment, timing boundaries must be explicit and identical across runs: setup and diagnostic checks should occur outside the timed section if the hypothesis concerns only the 1,200-second execution window, while all work designated as primary or replay execution must be included consistently.

## Gap

The retrieved literature is thin on the precise question. No cited source tests whether passing `docker info`, `docker version`, and `docker ps` predicts that six primary and six replay executions will all complete within 1,200 seconds on a fresh runner. Nor does it establish an expected completion rate or acceptable runtime margin for this artifact. A new experiment must therefore directly measure all twelve executions under a fixed runner configuration, record per-run elapsed time and terminal status, and evaluate the strict outcome “12 of 12 completed within the timed section.” Comparing primary and replay runs may additionally reveal cache warming or persistent-state effects, but such effects cannot be assumed from the available work.
