# Experiment design: Topic On a runner where `docker info`, `docker version`, and `docker ps` pass, do all six primary and six replay executions complete within the 1,200-second timed section? _(auto-enqueued follow-up from topic-can-make-reproduce-be-run-from-a-fresh-iso)_

**Hypothesis:** For six paired synthetic container fixtures in which the container's designated parent process exits 0 but a descendant either continues computing or keeps a declared output open, a naive parent-exit monitor will report all six as completed, whereas a process-tree-aware monitor will reject all six until every descendant has terminated and all declared outputs are closed; both monitors will accept six matched clean controls.

## Summary
Run 24 deterministic Docker executions—six dirty fixtures and six matched clean controls, followed by exact replays—to compare parent-exit-only completion against process-tree-and-output-aware completion within one 1,200-second timed section.

## Protocol
1. Implement a single Python 3.12 harness using only the standard library. Set PYTHONHASHSEED=1729 and random.seed(1729). Do not use runtime network access, external datasets, or Docker image pulls. Use a locally available, pinned Linux Python image, recorded by immutable image ID; prefer python:3.12-slim if already present. If no suitable local image exists, load a matching pre-provisioned OCI archive from the experiment bundle before the timed section. Build the fixture image before timing with docker build --network=none and FROM <immutable-local-image-ID>. Record the base and resulting image IDs.
2. Before scheduling any execution, set DOCKER_HOST=unix:///var/run/docker.sock and make that exact endpoint usable by the current runner user. On Linux, if necessary start the system daemon with systemctl start docker or service docker start; add the runner to the docker group and re-exec the harness with the new supplementary group, or grant that user access to /var/run/docker.sock. On macOS, start Docker Desktop, wait for its daemon, and ensure /var/run/docker.sock resolves to the active Docker Desktop socket. Never silently switch to a different endpoint and never run individual experiment commands through sudo.
3. From the final, non-root harness process, run docker info, docker version, and docker ps separately with 30-second timeouts. Require all three to exit 0 and save command, exit code, stdout, and stderr. Also run a pre-timing smoke container from the built image that executes python -c 'print(1729)' and require exit 0 and exact output 1729. If any gate fails, schedule zero fixtures, mark the run infrastructure_invalid and hypothesis_evaluated=false, and do not classify the hypothesis as refuted. Do not start the timed-section clock until every gate passes.
4. The container entry point is a Python monitor running as PID 1. For each execution it launches a designated parent process, records that parent's container PID and /proc/<pid>/stat starttime, and observes the same execution with two logical monitors. The naive monitor declares completion at the instant waitpid reports that the designated parent exited with code 0. The aware monitor polls every 0.01 seconds, recursively discovers descendants from /proc/*/stat PPID relationships while the parent or previously discovered descendants are alive, and identifies processes by the tuple (PID, /proc starttime) to prevent PID-reuse errors. It retains discovered descendants after reparenting. It declares completion only after the parent has exited 0, every discovered descendant identity has disappeared, and no process in the container has a file descriptor referring to a declared output. Detect open outputs by comparing device and inode from each /proc/<pid>/fd/* target with the device and inode of each declared output. Ignore permission-denied entries only if the process disappeared during the scan; any persistent scan error fails that execution.
5. Generate six dirty fixture types, each with one declared output /work/result.dat. All durations use time.monotonic(), and computing workers repeatedly calculate hashlib.sha256 over a fixed 4096-byte byte string until their specified duration expires. D1 cpu-child: one child computes for 3.0 seconds. D2 output-child: one child opens result.dat in append mode, writes and fsyncs 4096 deterministic bytes, then keeps the descriptor open while sleeping for 3.0 seconds. D3 cpu-output-child: one child opens and fsyncs result.dat and computes for 3.0 seconds while retaining the descriptor. D4 cpu-grandchild: an intermediate child spawns a grandchild that computes for 3.0 seconds; the intermediate remains alive for 0.75 seconds and then exits. D5 output-grandchild: an intermediate child spawns a grandchild that opens, writes, fsyncs, and retains result.dat for 3.0 seconds; the intermediate exits after 0.75 seconds. D6 split-children: one child computes for 3.0 seconds and a second child opens, writes, fsyncs, and retains result.dat for 3.0 seconds.
6. In every dirty fixture, each terminal worker first signals readiness only after computation has begun or the output descriptor has been opened. The designated parent waits for all readiness signals, then remains alive for exactly 1.0 second so the 0.01-second observer can discover the complete tree, and exits with code 0 without waiting for terminal workers. Thus terminal workers must remain active for approximately 2.0 seconds after parent exit. Treat failure to observe at least 50 polls during the readiness grace period as an invalid execution rather than a hypothesis result.
7. Create matched clean controls C1-C6 with exactly the same process topology, computation, output operations, and 3.0-second worker durations as D1-D6. The sole difference is that each clean designated parent waits for all descendants to exit and verifies result.dat is closed before it exits 0. Intermediate processes in grandchild controls are also waited for. This makes each dirty fixture plus its corresponding clean control one fixture pair.
8. Start CLOCK_MONOTONIC immediately before the first primary docker run. Execute sequentially in this fixed order: D1,C1,D2,C2,D3,C3,D4,C4,D5,C5,D6,C6, then replay the identical order as R-D1,R-C1 through R-D6,R-C6. These are six primary pairs plus six replay pairs, totaling exactly 24 container executions. Derive an execution seed as 1729 + fixture_index for primary executions and reuse the identical seed for the corresponding replay. Give each docker run a 30-second timeout, use --network=none, --init=false, --cap-drop=ALL, a read-only root filesystem, tmpfs for /tmp, and a unique bind-mounted result directory. Do not overlap executions.
9. For every execution, write an atomic JSON record containing fixture ID, dirty/control status, primary/replay status, seed, image ID, parent PID/starttime, parent exit code, all discovered descendant PID/starttime identities, declared-output open/closed samples, parent-exit timestamp, naive-completion timestamp, aware-completion timestamp, last-descendant-exit timestamp, final-output-close timestamp, docker start/end timestamps, timeout status, and invariant failures. Require each container and docker run to exit 0 and produce exactly one valid record.
10. At the exact parent-exit sample, compute naive_accept_at_parent_exit and aware_accept_at_parent_exit. Also verify the aware monitor never accepted at any earlier sample. For dirty executions require at least one tracked descendant to be alive or result.dat to be open at parent exit. For clean executions require no descendant alive and no declared output open at parent exit. Define aware safety lag as aware-completion time minus parent-exit time; define closure lag as max(last-descendant-exit time, final-output-close time) minus parent-exit time.
11. After all 24 runs, but before stopping the timed clock, validate records and create key_result.png with four bars showing the completion-at-parent-exit rate for naive/dirty, aware/dirty, naive/clean, and aware/clean. Use a fixed 0-to-1 y-axis, label every bar with its numerator over 12, and use deterministic colors. Write results.json containing all records, aggregate metrics, gate outputs, timed-section duration, hypothesis_evaluated, and verdict. Stop CLOCK_MONOTONIC only after results.json and key_result.png have been flushed and fsynced.
12. The timed section passes only if all 24 scheduled executions finish and both artifacts are written in at most 1200.000 seconds. The full experiment, including daemon/image preparation and gates, must finish within 30 wall-clock minutes. Classify the hypothesis as supported only if the timed-section condition holds; all 12 dirty executions have naive_accept_at_parent_exit=true and aware_accept_at_parent_exit=false; all 12 clean executions have both values true; every dirty aware completion occurs no earlier than max(last-descendant-exit, final-output-close), allowing only the 0.01-second polling resolution; every execution eventually receives aware acceptance before its 30-second timeout; and every primary/replay classification matches exactly. If all infrastructure and fixture-validity checks pass but any of those support conditions fails, classify it as refuted. Infrastructure or fixture invalidity yields hypothesis_evaluated=false, not refuted.

## Metrics
- Timed-section completion: number of valid executions completed out of 24 and elapsed CLOCK_MONOTONIC seconds from immediately before the first docker run through fsync of results.json and key_result.png; pass threshold is 24/24 and <=1200.000 seconds.
- Dirty naive completion-at-parent-exit rate: count of the 12 dirty primary/replay executions with naive_accept_at_parent_exit=true divided by 12; support requires 12/12.
- Dirty aware rejection-at-parent-exit rate: count of the 12 dirty executions with aware_accept_at_parent_exit=false divided by 12; support requires 12/12.
- Clean monitor acceptance rates: for the 12 clean executions, separately count naive_accept_at_parent_exit=true and aware_accept_at_parent_exit=true; support requires 12/12 for each monitor.
- Aware completion safety: for each execution compute aware_completion_time - max(last_descendant_exit_time, final_output_close_time); support requires every value to be >=-0.01 seconds and no earlier aware-accept sample.
- Dirty aware safety lag: aware_completion_time minus parent_exit_time; every dirty execution must have positive lag, while its parent must have exited 0 and at least one descendant or declared-output descriptor must still be active at parent exit.
- Clean monitor latency difference: absolute value of aware_completion_time minus naive_completion_time; require <=0.10 seconds for every clean execution, corresponding to at most ten polling intervals.
- Replay agreement: compare the dirty/control classification, parent exit code, naive parent-exit decision, aware parent-exit decision, and final aware decision between each primary execution and its replay; support requires exact agreement for all 12 matched primary/replay executions.
- Execution reliability: valid result records, successful docker exit, and eventual aware acceptance before the 30-second per-execution timeout; require 24/24.

## Time budget
30 minutes (ceiling 30).

## Expected outcomes
- **If supported:** All Docker gates exit 0; exactly 24/24 executions complete within 1200 seconds; dirty fixtures show naive completion at parent exit in 12/12 and aware completion at parent exit in 0/12, followed by aware completion only after descendants terminate and outputs close; clean controls show completion at parent exit for both monitors in 12/12; and all 12 primary/replay classifications agree. The figure therefore has bar heights 1.0, 0.0, 1.0, and 1.0 for naive/dirty, aware/dirty, naive/clean, and aware/clean.
- **If refuted:** With all infrastructure and validity checks passing, the hypothesis is refuted if any dirty execution is not accepted by the naive monitor at parent exit, any dirty execution is accepted by the aware monitor while a descendant or declared output remains active, either monitor rejects any clean control at parent exit, the aware monitor accepts before final descendant termination/output closure, any replay changes a classification, any execution fails to reach eventual aware completion, or fewer than 24 executions finish within 1200 seconds.
