# Literature survey: Can `make reproduce` be run from a fresh isolated checkout in a clean container or virtual machine, with the exact command, container or image identifier, interpreter path, exit status, stdout and stderr logs, generated hashes, and comparison against the released reference outputs reported?

Reproducible computational artifacts are generally understood as packages of documentation, data, and code that allow independent researchers to replicate and validate published findings [1]. Research compendia similarly package the paper, figures, data, and software, creating a structured object that can be inspected rather than treating the publication alone as the complete research output [4]. For the present question, however, packaging is only a prerequisite: the stronger test is whether a newly obtained checkout can execute through one documented entry point—`make reproduce`—without relying on unrecorded host state, prior build products, or the original authors’ knowledge. Arabas et al. emphasize precisely this distinction between an experiment that its author can rerun and one that another person can reproduce. Their case study identifies implicit assumptions, background knowledge, and unconsidered environmental factors as obstacles even when substantial effort has been made to support reproduction [2].

Containerization provides a practical method for reducing these environmental ambiguities. Canesche, Leissa, and Pereira describe Docker containers as bundles containing the software dependencies required to execute a tool and present a Docker-based methodology for constructing artifacts for independent evaluation [1]. Container-based operating-system virtualization is also motivated by isolation, accountability, and resource allocation, while offering performance improvements over earlier virtualization approaches [6]. These properties make a clean container or virtual machine an appropriate experimental boundary. Nevertheless, “runs in Docker” is not by itself a complete reproducibility result. A useful trial must identify the immutable or otherwise precise image used, start from a fresh checkout, disclose the exact invocation and interpreter path, and preserve the process exit status and separate stdout and stderr streams. These measurements distinguish successful unattended execution from procedures that work only after undocumented intervention. The retrieved literature supports isolation and comprehensive documentation, but it does not establish this exact metadata bundle as a standardized protocol.

The output test also requires care. Byte-identical hashes provide a strong and easily auditable comparison when released reference outputs are expected to be deterministic. Yet computational reruns can differ because of randomness, library-version changes, or environmental variation [3]. Hossain et al. therefore propose the Similarity-based Reproducibility Index for Jupyter notebooks, using output-type-specific similarity measures and scores between zero and one rather than requiring universal exact identity [3]. Although their method is notebook-specific, it clarifies the general distinction between execution success, exact artifact equality, and scientifically acceptable similarity. Accordingly, a `make reproduce` evaluation should report hashes for every generated deliverable and compare them with released reference hashes where available. Any mismatch should be characterized rather than collapsed into a binary result—for example, by identifying missing, extra, changed, or potentially nondeterministic outputs. Workflow research further indicates that computational workflows are intertwined with scientific outcomes and methodological innovations, reinforcing the need to evaluate the full automated path rather than isolated scripts [5].

## Gap

The retrieved work motivates artifact packaging, independent reruns, environmental isolation, workflow automation, and exact or similarity-based output comparison, but it does not report the proposed end-to-end test for this artifact. The open question is whether a fresh, isolated checkout actually completes via the literal command `make reproduce`, with no undocumented preparation, and whether its outputs agree with the released references. A new experiment should therefore record the checkout revision, container or VM identifier, interpreter path, exact command, exit status, complete stdout and stderr logs, generated-file inventory and hashes, reference hashes, and an explicit per-output comparison. This evidence would test not merely whether the artifact is available or containerized, but whether its advertised reproduction interface is independently executable and its results verifiable.
