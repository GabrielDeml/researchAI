# Experiment design: Topic **Does a larger evaluation budget reveal a success-rate difference?** Repeat the paired experiment at 100,000, 250,000, and 500,000 evaluations while retaining shared initialization and operator-schedule controls. These should be treated as distinct, prospectively specified hypotheses rather than retrospective extensions of the present result. _(auto-enqueued follow-up from genetic-algorithms)_

**Hypothesis:** Among paired runs in which neither algorithm has reached the optimum by 100,000 evaluations, serial populations will contain an average of at least one more fully solved all-ones trap-5 block in their best individual than matched frozen-parent batch-size-16 populations.

## Summary
Run 64 deterministically paired trap-5 genetic-algorithm comparisons and prospectively test, at 100,000, 250,000, and 500,000 evaluations, whether serial replacement yields at least one additional solved trap block in the best individual relative to frozen-parent batches of 16.

## Protocol
1. Use Python 3.11 with numpy, numba, scipy, pandas, and matplotlib; perform no network or file input other than package installation, and save outputs to a local results directory.
2. Generate a synthetic concatenated deceptive trap-5 problem with 20 nonoverlapping blocks, 5 bits per block, and genome length 100. Represent each block as an integer from 0 through 31. For a block containing u one-bits, assign score 5 if u=5 and otherwise assign score 4-u. Individual fitness is the sum over the 20 blocks, so the unique global optimum is the 100-bit all-ones string with fitness 100. A fully solved block is a block with value 31.
3. Use 64 prospectively fixed paired replicates, indexed r=0,...,63, with population size N=256. For replicate r, initialize one population by drawing every bit independently as Bernoulli(0.5) using numpy.random.Generator(numpy.random.PCG64(10000+r)). Use this exact initialized population for both algorithms in the pair. Assign each initial individual an independent uint64 tie-priority from the same initialization generator. Larger tie-priority wins fitness ties.
4. For each replicate, create one shared operator schedule of 499,744 offspring events using numpy.random.Generator(numpy.random.PCG64(20000+r)). For every event t, generate in this fixed order: four population indices uniformly from 0,...,255 for two size-2 parent tournaments; one crossover boundary uniformly from 1,...,19; one mutation block uniformly from 0,...,19; one mutation bit uniformly from 0,...,4; one replacement-target index uniformly from 0,...,255; and one uint64 offspring tie-priority. Store the schedule and give the identical arrays to both algorithms. Generate schedules one replicate at a time and discard them after both paired runs to limit memory use.
5. In each size-2 parent tournament, select the individual with greater fitness; break equal-fitness ties using greater tie-priority. Select two parents using the two scheduled tournaments. Construct one child by copying blocks before the scheduled block boundary from parent 1 and blocks at or after the boundary from parent 2. Then flip the scheduled bit in the scheduled mutation block. Compute the child's trap-5 fitness.
6. Use target-slot replacement for both algorithms. At the scheduled replacement target, replace the incumbent if the child has higher fitness, or if fitness is equal and the child's tie-priority is greater. Otherwise discard the child. This rule and the shared schedule must be identical between algorithms.
7. Serial algorithm: for every offspring event, select parents from the current population, construct and evaluate the child, and immediately apply target-slot replacement before processing the next event.
8. Frozen-parent batch-size-16 algorithm: process consecutive groups of exactly 16 offspring events. At the start of each group, freeze a snapshot of the population. Select all 32 parents and construct and evaluate all 16 children using only that snapshot. After all 16 children have been created, apply their target-slot replacements sequentially in event order to the live population. Thus the only timing difference is that parent selection and child construction are frozen for 16 events. The evaluation checkpoints align with complete batches because 100000-256, 250000-256, and 500000-256 are all divisible by 16.
9. Count the 256 initialized individuals as the first 256 fitness evaluations. Continue each run to exactly 500,000 total evaluations. At exactly 100,000, 250,000, and 500,000 evaluations, identify the population's best individual by maximum fitness with tie-priority as the tie-breaker, and record its fitness and number of value-31 blocks. Also record whether an optimum has been reached by that checkpoint; because replacement never accepts lower fitness over an optimum, current presence of an optimum is equivalent to having reached one.

Retain this same cohort for analyses at all three budgets, even if either algorithm reaches the optimum later. Do not redefine or filter the cohort at later checkpoints.

The deterministic primary decision at budget B is 'supported' if the arithmetic mean of d[r,B] over eligible pairs is at least 1.000 solved block and 'refuted' if it is below 1.000. Do not pool budgets, select the most favorable budget, or use later outcomes to alter the 100,000-evaluation cohort.

For each budget, report the 5th and 95th percentiles of bootstrap mean differences as a two-sided 90% percentile interval. This interval is descriptive and does not replace the prespecified mean-difference decision threshold. ## Metrics
- Primary paired solved-block difference at each budget: for the fixed cohort in which neither member reached fitness 100 by 100,000 evaluations, compute d[r,B]=serial solved blocks minus batch-size-16 solved blocks in the best individual, then report mean(d); supported at B iff mean(d)>=1.000, otherwise refuted.
- Bootstrap uncertainty: 5th and 95th percentiles of 20,000 bootstrap resampled eligible-cohort mean differences at each evaluation budget.
- Eligible cohort size: number and fraction of the 64 pairs in which neither algorithm reached the optimum by 100,000 evaluations.
- Optimum success rate at each budget: fraction of all 64 runs reaching fitness 100, reported separately for serial and batch-size-16 algorithms.
- Paired success-rate difference: serial optimum-success proportion minus batch optimum-success proportion at each budget.
- Paired success significance: exact one-sided McNemar/binomial p-value from serial-only versus batch-only successes, with Holm adjustment across the three budgets.
- Best fitness difference: eligible-cohort mean of serial best fitness minus batch best fitness at each budget, reported as a secondary structural-progress metric.
- Runtime: elapsed wall-clock minutes after numba warm-up, required to be no more than 30.

## Expected outcomes
- **If supported:** At one or more prospectively analyzed budgets, especially 250,000 or 500,000 evaluations, the eligible-cohort mean paired difference is at least +1.000 solved trap-5 block; a larger-budget success-rate effect is separately established only if serial has the higher success proportion and the Holm-adjusted paired McNemar p-value is below 0.05.
- **If refuted:** At each budget where the hypothesis fails, the eligible-cohort mean paired solved-block difference is below +1.000 and is therefore classified as refuted; the strongest false-pattern result would show differences near zero or negative, bootstrap intervals centered below +1, and no Holm-significant serial success-rate advantage.
