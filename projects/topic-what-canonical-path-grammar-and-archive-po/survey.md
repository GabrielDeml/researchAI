# Literature survey: Canonical path grammar and archive policy for rejecting ambiguous or colliding names

The retrieved literature directly supports treating archive member names as identifiers that require validation under a single, explicit canonicalization model—not merely as strings accepted by the host filesystem. Rappos shows that canonically equivalent Unicode characters may have several code-point representations and that filesystems handle them differently [1]. In the reported examples, NTFS can preserve distinct precomposed and decomposed names when files are created programmatically, whereas HFS+ applies a modified decomposition and may treat those names as the same file [1]. Windows also imposes character restrictions and reserves names such as `com1`, `prn`, and `nul` [1]. Thus, an archive that permits two byte-distinct names without checking their canonical equivalence may extract safely on one platform but collide, overwrite, or fail on another. This evidence favors an archive-wide comparison key derived from a specified Unicode normalization form, while retaining the original name only if it maps uniquely to that key.

Unicode normalization is necessary but may not settle all textual ambiguity. Work on Indic scripts shows that Unicode’s linear code-point representation can admit inconsistencies and malformed sequences involving connectors, conjuncts, and diacritics [4]. Its proposed language-aware normalizer and grapheme parser demonstrate that visual or orthographic identity may require more structure than generic code-point processing [4]. For archive policy, however, adopting script-specific linguistic equivalence would enlarge the collision relation and make implementations harder to reproduce. A narrower, testable policy is preferable: require well-formed Unicode, apply one named Unicode normalization algorithm and version, and reject duplicate normalized keys. The supplied work does not establish whether NFC, NFD, or another form is optimal for archive paths, nor does it evaluate case folding. Case-insensitive collisions and platform aliases therefore need separate policy rules rather than being assumed to follow from normalization.

Parser consistency is the other relevant body of prior work. Differential testing of JSON parsers found that imprecise specifications create semantic discrepancies and used consensus-based normalization to compare behavior across languages and runtime environments [2]. Similarly, VALARIN collects error features from multiple PDF parsers and reports that parsers exhibit shared biases when recovering from specification ambiguities; agreement on extracted error features was related to PDF safety [3]. Although neither study concerns pathnames, both support an applicable method: define the path grammar independently of any one archive library, generate adversarial names, and compare each implementation’s parse, normalization, rejection reason, and extraction destination. Consensus is useful for discovering discrepancies, but it should not define correctness, because multiple parsers may share the same recovery behavior or bias [3].

The available sources do not directly specify defenses against `..` traversal, absolute paths, mixed separators, repeated separators, drive-qualified paths, UNC-like forms, trailing dots or spaces, case-folding collisions, or duplicate archive entries. A conservative grammar should therefore be evaluated that accepts only relative paths composed of nonempty components separated by one designated separator; rejects `.` and `..` components, absolute or rooted syntax, control characters, and platform-reserved aliases; and requires uniqueness under both Unicode normalization and an explicitly chosen case/platform comparison profile. Standard experimental outcomes should include cross-parser agreement, rejection consistency, canonical-key collisions, and whether extraction remains inside the designated root. Tests should also verify order independence: changing archive entry order must not change which filesystem objects result.

## Gap

The specific open question is which exact canonicalization pipeline and alias set produce deterministic rejection across archive parsers and target filesystems without unnecessarily excluding valid international names. No retrieved study jointly tests traversal syntax, Unicode normalization, case folding, duplicate entries, Windows reserved names, and parser differentials. A new experiment should compare candidate grammars and canonical keys across multiple parser/runtime and filesystem combinations, using expected destination paths and collision detection—not parser consensus alone—as the principal correctness oracle.
