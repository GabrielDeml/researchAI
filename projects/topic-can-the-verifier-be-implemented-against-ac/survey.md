# Literature survey: Can the verifier be implemented against actual Git repositories, deriving tracked paths, blob identities, tree modes, symlinks, executable bits, submodules, and Git LFS semantics from an authenticated commit or tag?

The strongest motivation for a repository-aware verifier comes from software supply-chain security. Okafor et al. frame secure supply chains around transparency, validity, and separation, emphasizing that downstream assurance requires visibility into operations and evidence that each operation produced an authorized result [1]. For repository verification, this suggests that authenticating only a release label or top-level revision is insufficient unless the verifier can derive the precise repository state covered by that identity. Tracked paths, object identities, file modes, symlink targets, submodule references, and large-file indirections are therefore not incidental metadata: they determine what source inputs an authenticated Git state actually denotes. The survey’s observation that many supply chains were designed for sharing rather than security further supports testing these semantics against real repositories rather than assuming an idealized file tree [1].

The provided work does establish Git commits as practical units of historical analysis, although it does not address low-level repository verification. Wang and Hong’s Git-bisect framework traverses commit history and evaluates individual revisions, treating commits as concrete states on which predicates can be executed [2]. Their results are reported through success rate, failed traversals, and traversal time, while their discussion highlights complications from forks, merges, flaky predicates, and nonmonotonic histories [2]. These concerns imply useful experimental criteria for a verifier: deterministic resolution of a named commit or tag, agreement with an independent Git implementation, successful handling of repositories with nontrivial histories, and explicit failure when referenced objects are unavailable. However, their semantic analysis operates on code changes and behavior, not Git object graphs, tree entries, annotated tags, or checkout semantics.

Supply-chain attack studies reinforce why exact repository interpretation matters. GoSurf uses static analysis to identify language-specific attack surfaces in Go packages, showing that ecosystem semantics can expose risks omitted by generic taxonomies [4]. Dirty-Waters similarly operationalizes supply-chain “smells” in a tool and evaluates them across multiple project versions [5]. Maven-Hijack demonstrates that packaging order and runtime resolution can let an attacker alter effective behavior without changing the apparent main codebase or library names [6]. Collectively, these works indicate that verification must account for the mechanisms that determine effective inputs, rather than compare only visible names or ordinary source files. Applied to Git, this motivates adversarial fixtures involving duplicate-looking paths, mode changes, symlinks, submodule gitlinks, and Git LFS pointer files, although none of these studies directly evaluates such fixtures.

A further design lesson is that independently valid layers can still disagree. Nemecek et al. describe an “Integrity Clash” in which provenance and watermark checks both pass independently while making contradictory claims [10]. The analogous risk here is accepting an authenticated commit or tag while separately inspecting a working tree, archive, submodule checkout, or LFS-expanded directory that is not proven to be the exact interpretation of that Git identity. Accordingly, suitable metrics include semantic agreement per tree entry, coverage by entry type and mode, correct recursive object resolution, rejection of missing or malformed objects, and end-to-end agreement between authenticated identity and materialized content. The retrieved literature does not establish these as standard Git-verification metrics; they are experiment requirements derived from its broader emphasis on validity and cross-layer consistency.

## Gap

The supplied prior work does not demonstrate a verifier that begins with an authenticated Git commit or tag and reconstructs the complete repository state directly from Git objects. In particular, there is no reported experiment covering tracked-path enumeration, blob-identity binding, tree modes, executable bits, symlink representation, submodule gitlinks, tag peeling, or the distinction between Git LFS pointer blobs and externally retrieved LFS payloads. A new experiment should therefore test a real implementation against both representative public repositories and controlled adversarial repositories, compare its output with an independent Git implementation, and distinguish what is authenticated by the Git object graph from what requires additional authentication or network retrieval—especially submodule contents and LFS objects.
